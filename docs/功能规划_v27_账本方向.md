# 功能规划：从「爽感」改走「可信账本 + 长期视角」（v27 起）

> 2026-11-04 老板否决了游戏化方案：「打工是一个很长很复杂的事情，我看你的爽感基础包第一反应是反感，浮夸，实际需要的可能不是这个。」
> 结论：**撤销闪烁/扫光/连击/徽章/排行榜**，不再用短期刺激包装长期消耗。改做四件事，按老板选的顺序排期。

## 为什么改（设计立场）

| 游戏化假设 | 打工的实际情况 | 所以 |
|---|---|---|
| 高频、可重复、每一局独立 | 以年计、一次性消耗、带身体代价 | 不做即时奖励 |
| 用户需要被推着行动 | 上班的人已经被推得很紧了 | 不催、不打卡、不归零 |
| 数字越大越兴奋 | 更关心数字对不对、够不够、值不值 | 可信 → 可对账 → 长期趋势 |
| 缺少刺激就流失 | 缺少信任才流失 | 先解决"凭什么信" |

## A. 口径可追溯（信任的地基）

**做什么**：主界面上每个钱数都能点开看算式。

- 点「今天已赚」→ 浮层显示：`时薪 64.37 × 有效工时 4h45m = 305.76`，有效工时再拆成 `上班 08:30 → 现在 15:45（7h15m）− 午休 2h30m`
- 点「时薪」→ 显示 `月薪 9800 ÷ 21.75 天 ÷ 7 小时 = 64.37`，并标注"按 21.75 天折算，实际当月天数不同会有偏差"
- 点「本期已赚」→ 显示账期起止（10-16 → 11-15）、包含几天、每天各多少、哪些天是休息/病假/加班
- 每处都写清"含/不含个税、社保"——当前是**税前后都不含**，只按到手口径算，必须写明

**验收**：三个浮层都能打开、算式与主界面数字严格一致、账期边界与发薪日设置联动。

## B. 月末对账（解决"用两个月就不信"）

**做什么**：每月发薪日后，让用户填一次**实际到手**，工具算差异。

- 输入：实发金额（可选再填社保/公积金/个税代扣）
- 输出对比：`计时器估算 ¥5,580.32 / 实际到手 ¥5,412.68 / 差 ¥167.64（−3.0%）`
- 差异归因（按可能性给提示，不假装精确）：
  - 有请假/病假记录 → "本月有 1 天病假（按 60% 计），差 ¥180 左右对得上"
  - 有加班倍率记录 → "本月有 3 天 1.5 倍，估算偏高/偏低"
  - 无任何异常记录 → "当月工作日天数与 21.75 折算不一致，属正常折算差"
- 历史保存每次对账结果，形成"我的估算准确度"记录

**验收**：能录入实际金额；差异金额与百分比计算正确；有异常记录时能给出对应提示；历史对账可回看。

## C. 长期视角（我的时间在变值钱还是变便宜）

**做什么**：一条时间轴，而不是一天的排行榜。

- 时薪曲线：按月（或按工作阶段）记录"当时的时薪"，标出涨薪/换工作的节点
- 关键对比：`三年前同样 8 小时值 ¥380，现在值 ¥450（+18%）`、`换工作后时薪从 64 涨到 92（+44%）`
- 加班与收入的关系：`本月加班 18 小时，多赚 ¥1,240`，不评价好坏，只陈述事实
- 数据来源：当前按 settings 里的月薪+工时算；换工作后由用户改设置，曲线自动接上（可手填"从 2027-03 起月薪 12000"）

**验收**：能按月生成时薪点；节点标注可编辑；跨阶段比较的增幅计算正确。

## D. 安静的下班小结（不要庆祝，只要一句实话）

**做什么**：点「下班存档」后不弹窗、不放烟花，在页面上留一行可以摸到的字：

- `今天上班 7h00m，¥450.57。这个月第 12 天，累计 ¥5,412.68。`
- 需要时点一下展开细节（今日/本月/本年三行），不需要就划走
- 没有徽章、没有音效、没有"恭喜"

**验收**：存档后出现一行小结，内容与主界面一致；点击可展开/收起；不遮挡主数字。

## 排期建议（待老板拍板顺序）

| 顺序 | 版本 | 内容 | 我的理由 |
|---|---|---|---|

## 老板定的产品基调（2026-11-04）

> 「这个东西应该给人的感觉是**确定的、可信的、有一种支撑感**。」

落到设计上，三条硬标准：

1. **确定**：同一个页面刷新两次，数字必须一样；任何"估"的地方都标出来（如"按 21.75 天折算，实际月份会差几十块"），不含糊。
2. **可信**：每个数字都能倒推回去；对不上时工具主动说"为什么对不上"，而不是等用户怀疑。
3. **支撑感**：不制造焦虑（不催打卡、不排行、不归零），只做"你的账我替你记着"的底色；用户看完的感觉应该是"心里有数了"，不是"我又被卷了"。

## v27 实现规格：月末对账（B）

### 数据

```js
// localStorage: niuma.actuals.v1
[{
  periodKey: "2026-10-16~2026-11-15",  // 与 periodRange() 一致
  estimate: 5580.32,                    // 当时的计时器估算（保存快照，不随后重算）
  actual: 5412.68,                      // 用户填的实发
  diff: -167.64,
  diffPct: -3.0,
  deductions: { social: 608, housing: 200, tax: 104.88 },  // 可选
  note: "",
  at: 1730800000000
}]
```
- 同时写进 IDB 快照（`persist()` 里加 `actuals`），保证清 localStorage 后能水合回来。

### 交互

1. 主界面「本期构成」卡片下方新增 **「月末对账」** 卡片：
   - 未对账：「本期估算 ¥5,580.32 ｜ 拿到工资后填一下实际到手 →」+ 按钮「填入实际」
   - 已对账：显示 `估算 ¥5,580.32 / 实际 ¥5,412.68 / 差 −¥167.64（−3.0%）` + 「修改」「看历史」
2. 点「填入实际」→ 自定义浮层（不用 prompt）：实发金额（必填）、社保/公积金/个税（折叠可选）、备注
3. 保存后 → 结果面板（同一浮层内切换）：
   - 三个大数字横向：估算 / 实际 / 差额（差额正绿负红）
   - **差异归因**（按该账期记录自动生成，最多 3 条，按影响金额排序）：
     - 有 `sick` 天 → 「病假 N 天，按 60% 计，影响 −¥X」
     - 有 `off` 天 → 「休息 N 天，不计钱，影响 −¥X」
     - 有 `paid` 天 → 「带薪假 N 天，按 100% 计」
     - 有 `ot` 天 → 「加班 N 天（1.5/2/3 倍），影响 +¥X」
     - 始终追加一条折算说明：「当月工作日 N 天，按 21.75 天折算，本身会有几十元偏差」
   - 底部一句结论：`差额主要来自 1 天病假（−¥180）和折算（+¥12）` 或 `没有异常记录，差额属于折算偏差`
4. 「看历史」→ 显示最近 6 次：账期 / 估算 / 实际 / 差额 / 偏差率 / 时间，附一行汇总「平均绝对偏差 2.7%」

### 断言（改前必红）

1. 对账差值与百分比计算（含负数、含 actual=0 边界）
2. 归因：构造含 sick/off/paid/ot 的账期 → 各条金额正确、排序正确
3. 无异常记录 → 只出现折算说明，不出现病假/加班文案
4. 保存后写入 localStorage 且 IDB 快照包含 actuals
5. 历史列表最多 6 条、按时间倒序
6. 同一账期再次对账 = 覆盖而非新增
7. 估算快照不被后续改月薪影响（保存时固化）

## v28 实现规格：口径可追溯（A）

### 目标
点页面上任何一个钱数，都能看到它是怎么算出来的；看完不需要人解释。

### 交互
1. 主界面可点的三处：**今天已赚**、**时薪卡**、**本期已赚**（各自 a11y：`role=button`、`cursor:pointer`、右下角一个极小的 `?` 标）
2. 点击 → 底部抽屉（drawer）从下往上推，不遮住主数字的上半部分；再点或按 Esc 关闭
3. 抽屉内容按「结论 → 算式 → 说明」三段：

```
今天已赚 ¥305.76
────────────────────────
时薪 ¥64.37 × 有效工时 4h45m = ¥305.76
有效工时 = 上班 08:30 → 现在 15:45（7h15m）− 午休 2h30m
────────────────────────
说明：按设置里的月薪 9800、21.75 天、7 小时折算；
     不含个税与社保（本工具只按到手口径估算）；
     加班日按倍率另计。
```

4. 「时薪」抽屉：
```
时薪 ¥64.37
────────────────────────
月薪 9800 ÷ 21.75 天 ÷ 7 小时 = 64.37
日薪 450.57 = 月薪 9800 ÷ 21.75 天
────────────────────────
说明：21.75 是月均计薪天数（(365−104)/12），当月实际工作日会多几天，
     所以月末对账可能有几十元偏差；可在月末对账里校准。
```
5. 「本期已赚」抽屉：
```
本期 ¥5,580.32
────────────────────────
账期 10-16 → 11-15（发薪日 15 号），共 21 个工作日
其中：正常 18 天 ¥8,110 / 病假 1 天 ¥270 / 休息 1 天 ¥0 / 加班 1 天 ×1.5 ¥676
合计 ¥5,580.32
────────────────────────
说明：每天的金额可在日历里点开查看；被标记为休息/病假的天按规则折算。
```

### 一致性硬要求
- 抽屉里的数字必须**直接复用**主界面同一函数（`amountOf` / `dayValue` / `periodTotal`），禁止另写一套算式——否则迟早对不上。
- 断言：抽屉数字 === 主界面数字（同一假时钟下）；三类抽屉都能开/关；Esc 可关；关闭后不留遮罩。

## v29 实现规格：长期视角（C）

### 目标
不看「今天赚多少」，看「我的时间在怎么变值」。这是打工人十年尺度上唯一有意义的量。

### 数据
`niuma.phases.v1`：阶段数组，每段是一次"薪资状态"：
```js
[{ from: "2024-01", salary: 7000, days: 21.75, hours: 8, note: "科东·派遣" },
 { from: "2026-04", salary: 8800, days: 21.75, hours: 7, note: "合邦·转正" }]
```
- 首次使用时自动用当前设置生成第一段（from = 当月）
- 用户改月薪/工时 → 自动追加一段新阶段（同月内改则覆盖最后一段），不需要用户手动维护
- 存储与 IDB 同步（`persist()` 加 `phases`）

### 展示
主界面新增卡片「我的时间值多少」（放在对账卡片之后，折叠态默认收起，不打扰）：

```
时薪轨迹
2024-01  ¥40.23   ├───────────────
2026-04  ¥57.83   │        ╱
2026-11  ¥64.37   │  ╱─────
                  └────────────── 
两年半涨了 60%（¥40.23 → ¥64.37）
同样 8 小时：2024 年值 ¥321.85，现在值 ¥514.96
```

- 用 CSS 画折线（不引图表库）：x=时间，y=时薪，点旁标注时薪
- 三个关键句自动生成：
  1. `从 A 到 B，时薪涨了 X%（¥a → ¥b）`
  2. `同样 8 小时，当时值 ¥x，现在值 ¥y`
  3. 若涨幅 < 5%：`这 X 个月时薪基本没动` —— **这句话是产品的良心，必须说**
- 阶段可编辑（改 from/salary/note），改完曲线与三句话立即重算

### 断言
1. 首次使用生成初始阶段（from = 当前月）
2. 改月薪 → 追加新阶段；同月再改 → 覆盖最后一段而非新增
3. 涨幅计算（含 0%、负增长：`降了 X%` 也要正确、不能说"涨了 -X%"）
4. 「同样 8 小时」换算正确
5. 涨幅 <5% 时出现"基本没动"文案
6. 阶段编辑后曲线点数量与三句文案同步更新
7. 存储 + IDB 快照含 phases
