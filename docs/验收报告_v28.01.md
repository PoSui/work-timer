## 发现的问题（按严重度排序）

### P2-1（不阻断本次发布，建议 v29 修）满勤基准用「当前日薪」，旧对账的解释会随调薪漂移

复现（PM88）：先生成一条病假对账——estimate ¥5406.90、actual ¥5226.67、diff −¥180.23，结论「差额主要来自 1 天病假（−¥180.23）」。随后把月薪改成 20000（日薪 450.57 → 919.54），重开该条点「修改」再保存：`estimate` 与 `diff` 都不变（快照仍 5406.90 / −180.23），但归因按新日薪重算，结论变成「差额主要来自 1 天病假（−¥367.82）。剩余 +¥187.59 暂未归类…」。

判 **P2 起**，理由：本产品的核心承诺是「账本自洽、说清差在哪」。estimate 和 diff 已经冻结（这是对的），但「差在哪」的解释仍依赖浮动的当前日薪，导致**同一笔历史账在调薪后给出两个不同数字**。用户不会区分「估算快照」和「归因重算」，只会觉得账本前后矛盾；这种不信任一旦产生，比多显示一个错误数字更难修复。它不构成 P1 的原因：需要用户主动调薪并重新编辑保存才触发，数据本身没被改写，当月的填报与结论仍一致。

建议修法（不本次）：保存记录时把归因所需的最小快照一并落库——`pay`（当时日薪）、`workdays`、以及每条 `impact`（或直接存结论文本）。显示结果页时优先用快照；缺快照的旧记录才回退当前日薪。若嫌字段多，至少存 `pay` + `workdays`，归因就能按当时基数重算，不会漂移。文档取舍 #2 已披露「改月薪后归因金额会变」，属于知情披露，不等于修复。

### P3（建议，不阻断）

- **P3-1 同段自相矛盾**：PM81 diff=0 时结论先说「不需要解释差额」，紧接着又说「剩余 +¥180.23 暂未归类…」。原因是 Σ归因净额 −180.23（sick −180.23 + off −450.57 + ot +450.57）与实发=满勤不一致。建议当 |baseDiff|<1 但 |residual|>100 时改写为「实发与满勤一致，但你标记的病假/休息/加班净影响 −¥180.23 未体现在实发里，剩余 +¥180.23 待核」。
- **P3-2 两个「差」并存**：PM84/PM85 结果页顶部仍显示原始 `diff`（PM84 显示 −¥1500.00），结论里的「差 +¥0.00」用的是代扣后差额，两处未标注口径。建议顶部标签写「与满勤应得差」，结论写「扣代扣后差」，或同时显示两个数。
- **P3-3 抵消只在结论层合并**：PM82 结论已说「基本抵消」，但归因卡明细仍分行「休息 −¥450.57 / 加班 +¥450.57」。若产品目标就是「不让用户自己算抵消」，明细也应合并为一行或折叠展示。
- **P3-4 旧口径残留**：`app.v8.js:569` / `index.html:1018` 的「时薪」抽屉说明仍写「月末对账可能有几十元偏差」，与 v28.01 对账口径（残差 >100 才提示、且不再说几十元）不一致。建议改为「当月实际工作日与月均天数不同，对账会按满勤应得校准，差额会在结果里列出」。
- **P3-5 提醒可能误报**：代扣很高导致实发 <0.3×满勤应得时，按代码会提示「只发了半个月或一部分」，但原因其实是代扣。建议该提醒先扣除已填代扣再判断，或文案加「若已填代扣可忽略」。
